# API Reference

Base URL (local): `http://localhost:58000`. Interactive OpenAPI docs are auto-generated by FastAPI at `/docs` and `/redoc` — this document explains the *why* behind each endpoint; the schemas there are always the source of truth for exact request/response shapes.

## Authentication

Two independent mechanisms, matching the two kinds of caller (`services/api/app/auth.py`):

- **Service API key** (`X-API-Key` header) — for the six simulated systems calling `POST /v1/calls`. Configured via `SERVICE_API_KEYS` (`system:key,system:key`). The key determines the `system` value used for attribution and budget lookup — a caller cannot claim to be a different system than its key belongs to.
- **JWT bearer token** (`Authorization: Bearer <token>`) — for the human dashboard user and all admin/read endpoints. Obtained via `POST /v1/auth/token` (OAuth2 password flow) against the single configured admin account (`ADMIN_USERNAME`/`ADMIN_PASSWORD`). No multi-user system exists yet — see `docs/architecture.md` §7.

## `POST /v1/auth/token`

OAuth2 password grant. Form-encoded body: `username`, `password`. Returns `{"access_token": "...", "token_type": "bearer"}`. No rate limiting is implemented on this endpoint in this build — a real deployment should add one (brute-force protection against the single admin account).

## `POST /v1/calls`

**Auth:** service API key. The only way anything in this codebase reaches Bedrock — see `packages/ledger_core/wrapper.py::call_model`.

Request:
```json
{
  "decision_type": "fabric_query",
  "customer_identifier": "cust_884210",
  "messages": [{"role": "user", "content": [{"text": "does this saree run true to size?"}]}],
  "system_prompt": null,
  "decision_id": null,
  "attempt_number": 1
}
```

`decision_id`/`attempt_number` let a caller retrying the same underlying task group attempts under one decision — pass the same `decision_id` back with an incremented `attempt_number` on a retry.

Responses:
- `200` — `{"decision_id", "attempt_number", "status", "model_id", "output_text", "cost", "customer_id", "request_id"}`. `status` is one of `success` | `degraded` (the graceful-degradation fallback fired).
- `400` — no `DecisionTypeConfig` exists for this `(system, decision_type)` — nobody has deliberately set a ceiling for it yet; the system never spends against an unconfigured decision type.
- `429` — budget ceiling reached; body includes `system`, `decision_type`, `spent_today`, `ceiling`. A record of the block is written to the ledger (`status="blocked"`, `cost=0`) before this response is returned.

## `GET /v1/ledger/summary?start=YYYY-MM-DD&end=YYYY-MM-DD`

**Auth:** JWT. Spend by `(system, decision_type)` over a date range, including `cost_per_decision`. Defaults to the last 7 days.

## `GET /v1/ledger/customers/{canonical_id}`

**Auth:** JWT. Total attributed spend for one canonical customer, across every system, by decision type. Empty `rows` most commonly means the customer's activity predates their identifiers being linked — this is a real, honestly-surfaced limitation, not a bug (identity resolution applies going forward only).

## `GET/PUT /v1/budget/configs`

**Auth:** JWT. `GET` lists every configured `(system, decision_type)`. `PUT` upserts one — `enforcement_mode` (`hard_stop`|`degrade`), `daily_ceiling`, `routing_model_id`, `fallback_model_id` (required if `degrade`), `reservation_estimate` (the conservative per-call amount reserved atomically before a real cost is known — see `docs/architecture.md` §7 on the concurrency design).

## `GET/PUT/DELETE /v1/budget/calendar-overrides`

**Auth:** JWT. A date-scoped ceiling that beats the default on a known high-demand date. `PUT` is an upsert — re-approving an override for a date that already has one updates it rather than erroring, matching this system's own "a person can revise a deliberate decision" discipline. `DELETE` requires `system`, `decision_type`, `override_date` as query params.

## `GET /v1/budget/status?system=...&decision_type=...&date=YYYY-MM-DD`

**Auth:** JWT. Current spend vs. ceiling for one `(system, decision_type)` — reads the real-time Redis running total plus whichever ceiling (default or calendar override) is in effect for the given date.

## `GET /v1/budget/events?system=...&limit=100`

**Auth:** JWT. The audit trail: every `hard_stop`, `degrade`, `fail_open`, `fail_closed`, ordered newest-first.

## `POST /v1/identity/link`

**Auth:** JWT. `{"system", "raw_identifier", "canonical_id"?}` — links one system's local identifier to a canonical customer account (creates a new account if `canonical_id` is omitted). Refuses (`409`) to silently reassign an already-linked identifier to a different account — an explicit rejection of fuzzy matching.

## `GET /v1/identity/resolve?system=...&raw_identifier=...`

**Auth:** JWT. Returns the canonical ID for a local identifier, or `unresolved:{system}:{raw_identifier}` if never linked.

## `POST /v1/reconciliation/run` / `GET /v1/reconciliation/runs`

**Auth:** JWT. Compares the wrapper's real-time cost estimate against an actual invoice, at model/usage-type grain (the finest grain AWS's own CUR actually provides). `POST` accepts a CSV upload in the shape documented in `database/seed/sample_invoice.csv`; a real deployment would point this at an actual CUR export instead.

## `GET /health`, `GET /ready`, `GET /metrics`

`/health` — liveness, no dependencies checked. `/ready` — checks Postgres and Redis are actually reachable. `/metrics` — Prometheus exposition format.
